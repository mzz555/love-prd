## 1. 为什么要做这次复盘

截至 2026-10-27，技术回执记录：第二轮七对数据的 V0.3 模拟复核运行中，2,802 条 rule 断言全部通过、123 条 judgment 无差异、预览扫描零命中；七对在 S0 至 S3 场景下均未达到共同交付条件。

这说明当前引擎能够按既定规则稳定执行，并不等于当前采集材料足以支持共同交付。已有技术回执已对主要阻塞作出初步分类，但这些分类还需要被整理成明确的产品问题和可验证的二阶段设计输入。

如果不先进行有限诊断就直接设计新追问，可能无法区分：问题是资料本身不足、事件无法可靠对应、标注或事实仍待确认、规则有意阻止输出，还是实际实现存在需要单独调查的问题。若将这些不同原因一概归为“追问不足”，可能造成无效提问、重复采集，甚至诱导用户给出预期答案。

因此，本次复盘的目的不是重做阶段一验收，而是利用现有结果，确定二阶段应优先验证哪些采集和追问假设。

## 2. 本次复盘的目标

本次复盘应回答以下问题：

1. 七对数据当前未达到共同交付条件的主要阻塞分别是什么？
2. 每个阻塞有何可追溯的输入、标注、规则或运行结果作为依据？
3. 阻塞初步属于哪一类：资料不足、事件对应不足、标注/事实待核、规则边界、实现问题，或目前无法判断？
4. 哪些问题有理由尝试通过二阶段采集或追问改善，哪些问题不能假定可由追问解决？
5. 应形成哪些可被目标用户试答和后续数据验证的设计假设？

**本次复盘不以提高共同交付率为目标，不预设七对资料一定能够通过补问达到共同交付。** 资料不足、未知、未确认和权限限制仍应如实保留；不得为了产出结论而降低既定证据标准。

## 3. 范围与边界

### 3.1 本次要做

- 以现有 V0.3 技术回执、已有标注状态、规则说明和运行结果为起点。
- 先汇总七对的主要阻塞，再挑选约 3—4 个有代表性的阻塞类型深入检查。
- 对每个代表性案例按“输入与证据状态 → 标注/规则 → 引擎判断 → 交付阻塞 → 可考虑的产品措施”核对。
- 区分已确认事实、合理推断、待验证假设和目前无法判断的事项。
- 将可干预的问题转化为二阶段追问设计输入，并为假设指定验证方式。
- 记录暂不处理事项和后续责任人。

### 3.2 本次不做

- 不从头逐条重审七对全部标注，不要求重新完成已裁决的 V0.3 流程。
- 不重跑已被技术确定为正式结果的测试；如发现新的、具体且可复现的技术疑点，另行登记议题，由技术判断是否需要针对性复现。
- 不重新打开已经裁决的个别标签、回答或预期；只有出现新的相关证据时，才提出单独复核请求。
- 不修改引擎、SPEC、PRD、预期值或历史数据，不在本次会议上直接批准开发变更。
- 不因七对都未共同交付而认定模型方向失败，也不把追问不足认定为唯一原因。
- 不在本次复盘中评价量表的心理测量有效性或替代正式授权核验。
- 不以完成复盘为由扩大原始资料的访问范围。

## 4. 受控环境与资料保护要求

1. 原始问卷、完整回答、工作簿、逐条证据和包含可识别信息的运行产物，只能在已确认具备访问控制的私有环境中查看和处理。
2. 公开仓库只记录不含参与者作答内容的汇总结论、规则依据、决策和版本信息；不得将原始回答、完整标注表、真人资料包、可还原身份的截图或逐条敏感内容提交至公开仓库。
3. 复盘前先确认原始资料的实际存放位置、访问权限及授权用途。如发现真实资料处于公开可访问位置或公开历史提交中，应停止继续传播并另行处理权限、移除和必要的历史清理；该事项不以本次复盘结项为条件。
4. 尽量使用参与者代号、汇总计数和最小必要证据。只有为判断某个具体问题所必需时，授权人员才在受控环境中查看对应材料。
5. 不将真实回答复制到未获批准的第三方工具、公共会话或公开问题讨论中。
6. 原始资料保持不变；如确需试验性修改或运行，应使用受控副本并标明用途和版本。复盘结论不得反向覆盖原始记录。
7. 访问权限、保存期限、删除责任或载体尚未明确时，不得自行假定已经合规；将未决事项登记并交由相应责任人确认。

## 5. 职责分工

### 5.1 技术负责

**需要做：**

- 提供并解释现有 V0.3 技术回执中已记录的七对整体结果和主要阻塞分类。
- 对选定的代表性案例，说明实际输入/证据状态、对应规则或 SPEC 条款、引擎输出及其如何导致当前交付状态。
- 明确区分“资料本身不足”“规则按设计阻断”“事实/标注待核”“疑似实现问题”和“现有证据不足以判断”。
- 指出哪些结论已有运行记录支持，哪些只是可能原因；不确定处明确标记，不要求当场猜测。
- 对拟议的追问方向提供技术边界意见：现有系统能否表达、哪些数据结构或规则可能受影响、后续若需改动应如何另行定义验收。
- 复核复盘文档中有关引擎行为、规则和技术结论的表述是否准确。
- 如发现新的、具体且可复现的技术疑点，提出是否需要另行登记和针对性验证的建议。

**本次不需要做：**

- 不重新审核七对所有标注，不重跑已确认的完整测试套件。
- 不为本次复盘预先开发新功能、修改引擎或改写 SPEC。
- 不擅自更改历史输入、标注、预期值、交付状态或已裁决结论。
- 不替产品决定哪些洞察有用户价值、哪些追问应纳入正式题本。
- 不把“技术上可以实现”直接等同于“产品上应该采用”。
- 不为使七对数据达到共同交付而放宽规则或补造证据。

### 5.2 产品负责

**需要做：**

- 说明本次复盘要支持的产品决策，并确保讨论始终围绕二阶段的采集和追问问题。
- 根据技术提供的证据，判断某个阻塞是否可能通过题目、提示、追问触发条件或交互流程改善。
- 对每项可能的改进写清：要解决什么缺口、为什么值得问、需要收集什么信息、用户拒答或仍不清楚时如何处理、后续如何验证。
- 将“已确认事实、推断、待验证假设、暂不处理”分开记录，避免把推测写成产品规则。
- 主笔《七对数据诊断与二阶段设计输入》，记录结论、分歧、责任人及待确认事项。
- 将经讨论形成的设计假设带入追问题本、模板和词表工作；后续是否修改正式产品要求，另行走产品与技术共同确认的流程。

**本次不需要做：**

- 不替技术推断代码执行路径，不在缺少技术证据时自行认定为引擎缺陷。
- 不直接修改引擎、SPEC 或技术实现方案。
- 不为了“解释得通”而擅自重标历史数据或改动已裁决事项。
- 不假定所有阻塞都能通过增加追问解决。
- 不将复盘中的假设直接写成已验证的产品事实，也不在本次会议上要求技术承诺未经验证的实现。

### 5.3 共同责任与需要时的协助

- 产品与技术共同确认：事实是否有依据、原因分类是否准确、该问题是否值得进入二阶段。
- 对分歧先明确属于事实、技术解释、标注语义还是产品取舍，再由相应责任人提供证据；不得以角色权威代替证据。
- 若关键争议确实涉及标注语义或原标注者难以独立判断，再请龚老师或适当的独立复核者只处理具体争议项，不将本次工作扩大为七对全量重审。
- 产品负责产品需求与交付价值判断；技术负责技术行为、实现边界与技术验证。跨职责的变更在双方讨论后形成明确记录，技术对最终技术实现与验收保留确认权。

## 6. 执行步骤

### 第一步：技术整理现有证据

技术以现有回执为基础，为七对各整理一条汇总记录，至少包括：

- 当前交付状态及主要阻塞；
- 可追溯的规则、输入/证据状态或运行记录；
- 初步原因类别；
- 已确认事实与尚未确认事项；
- 是否有理由认为追问可能改变该阻塞。

该表只做汇总，不复制原始作答或完整标注内容。

### 第二步：产品整理待回答的产品问题

产品依据第一步结果，列出可能与采集、题目理解、本人体验表达、事件锚定或拒答处理有关的问题。每个问题都应说明其与二阶段工作的关系，不提前认定根因。

### 第三步：共同选择代表性案例

先看七对整体分布，再选取约 3—4 个具有代表性的阻塞类型。建议覆盖：

- 单侧缺少清楚的本人体验；
- 双方均缺少清楚的本人体验；
- 双方均有体验但事件对应未确认；
- 局部证据/标签修订后，整体交付状态仍未改变。

这些是案例选择方向，不要求每一类都重新审核所有相关数据。若现有证据不足以支持某类分析，记录为待核即可。

### 第四步：按统一路径讨论每个案例

对每个入选案例依次回答：

1. **现象：** 实际结果是什么？
2. **证据：** 哪些输入状态、标注、规则或运行结果支持这一解释？
3. **原因类别：** 资料不足、事件对应不足、标注/事实待核、规则边界、实现问题，还是无法判断？
4. **可干预性：** 追问是否可能改善？依据是什么？哪些情况即使追问也不能保证解决？
5. **产品假设：** 如果要尝试改善，最小的题目或追问调整是什么？
6. **验证方式：** 用目标用户试答或后续受控数据检查什么结果？
7. **决定：** 纳入二阶段设计、另开技术议题、需专项复核，或暂不处理。

### 第五步：形成二阶段设计输入并结束本次复盘

产品将已确认的障碍、待验证假设、拟采取的措施和验证方法整理成主文档。技术确认其中的技术描述、规则引用和实现边界。未达成一致的事项保留为开放问题，不在本次复盘中强行裁决。

## 7. 最终产物

本次只要求形成一份主文档：

**《CORE 第二轮七对数据诊断与二阶段设计输入》**

主文档应包含以下四部分：

1. **七对总体诊断表：** 每对的主要阻塞、原因类别、证据依据、结论状态及是否可能通过追问改善。
2. **代表性案例分析：** 对约 3—4 个案例按统一路径记录现象、证据、原因、可干预性和结论。
3. **二阶段设计假设表：** 每项假设对应的问题、拟议措施、验证方式、责任人和状态。
4. **暂不处理与待核事项：** 明确哪些事项不重开、哪些需要单独调查，以及哪些结论尚不能下定论。

文档中不得包含真实回答、完整标注表或不必要的参与者细节。若需要说明具体证据，优先引用现有脱敏回执、规则条款和版本记录。

本次不要求另行产出新的代码、引擎版本、完整测试报告或重标数据包。如后续发现需要技术修改，应另行定义需求、影响范围和验收条件。

## 8. 完成标准

同时满足以下条件，才算本次诊断复盘完成：

- 七对数据的主要阻塞均有汇总记录；无法确定的原因明确标记为未知或待核。
- 已区分资料不足、事件对应不足、标注/事实待核、规则边界和实现问题，不把所有问题统一归因于追问不足。
- 已对少量代表性案例完成有证据的分析，且未扩大成全量标注复审。
- 形成少量具体、可验证的二阶段设计假设，并明确验证方式和责任人。
- 产品与技术已确认文档中的事实、技术描述、产品含义和后续行动；尚有分歧的事项单独列明。
- 原始资料始终在受控环境中处理；公开仓库只保留脱敏的结论与决策记录。
- 没有因为本次复盘而擅自修改已裁决的历史数据、规则或验收结果。
